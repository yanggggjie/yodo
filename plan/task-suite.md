# 任务集：衡量学习效果

## 决定一览

| 问题 | 决定 |
|---|---|
| 评什么 | 学习效果：学得快不快、学会的 task 能不能在新参数上完成。不评录制算法 |
| 名字 | 任务集（不是数据集）。每条任务是一个可执行的标准 |
| 账号 | 测试账号，允许任何操作（点赞、发布、删除等），不做风险分级 |
| 任务来源 | 你自己常做的事；站点热榜与导航里的热门操作；SaaS 帮助中心的常见流程 |
| 任务格式 | 一个 JSON 文件一个任务 |
| 演示 | 按意图在录制窗口里操作一遍，只产出录制 |
| 学习 | 学习者只拿到录制目录和意图，写草稿 task，最多 5 轮 |
| 学会的标准 | 草稿在至少两组未见过的参数上通过评分 |
| 评分 | 确定性脚本，不用 agent 判断 |
| 运行方式 | 串行、可断点续跑、单任务失败不影响其它任务 |
| badcase | 每个失败任务一份结构化记录，带失败类别和证据，失败集合可反复重跑 |
| 不做 | 运行耗时、录制真值、录制召回精度、分析者角色、多次学习的方差统计、版本化与漂移检测 |

## 1. 任务格式

```json
{
  "id": "xhs-search-open-note",
  "site": "https://www.xiaohongshu.com",
  "intent": "搜索 {query}，打开第 1 篇笔记",
  "params": {
    "demo": { "query": "咖啡" },
    "test": [{ "query": "露营" }, { "query": "手冲" }]
  },
  "check": "结果标题或正文包含 {query}"
}
```

- `demo` 只用于演示，学习者不能看到 `test`。
- `test` 至少两组。学习者只能看到参数名，不能看到具体值。
- `check` 尽量写成可自动判断的条件；无法自动判断的，人工看结果后在记录里标注。
- 测试账号允许任何操作，任务可以写明“发布”“删除”等动作。是否执行由任务本身决定，不做额外限制。

## 2. 环节

| 环节 | 执行者 | 输入 | 输出 |
|---|---|---|---|
| 演示 | agent，在录制窗口里按意图操作 | `intent` 与 `demo` | 录制目录 |
| 学习 | agent，独立会话 | 录制目录、`intent`、`test` 的参数名 | 草稿 task |
| 评分 | 脚本 | 草稿 task、`test` 的每组参数、`check` | 每组是否通过，以及运行输出 |

学习者的输入只能是录制目录和意图。不给演示者的思路、不给源码、不给 dev 接口、不给其它任务。

学习的一轮：写草稿 → 用 `demo` 参数试跑一次 → 看结果，不通过则带着错误信息进入下一轮。试跑通过后交给评分。

## 3. 跑完整个任务集

### 3.1 运行器

一个脚本 `scripts/suite/run.mjs`，负责顺序执行所有任务。它只做调度，不做判断：

- 按 `id` 排序，逐个执行；每个任务的所有步骤（演示、学习、评分）完成后才进入下一个。
- 每个任务写入独立目录 `~/.yodo/suite/<运行号>/<任务 id>/`，包含录制引用、学习轮次记录、评分结果。
- 单个任务的失败（超时、异常、学习者崩溃）只记录到该任务，不中断整体。
- 站点不可达或登录失效的任务，记为“环境失败”，不占用学习轮次。

### 3.2 断点续跑

- 运行号固定在开始时生成，中断后用同一运行号继续。
- 已完成（学会或达到 5 轮）的任务跳过；未完成的任务从当前环节重新开始，丢弃未完成环节的部分产物。
- 运行器在每个任务结束时写入一行状态到 `status.jsonl`，续跑时以此为准，不依赖内存。

### 3.3 超时

- 演示：单个任务最多 10 分钟。
- 学习：单轮最多 5 分钟，全部最多 5 轮。
- 评分：每组参数最多 2 分钟。
- 超时都按失败记录，并写明是哪个环节超时。

### 3.4 环境检查

每次运行开始前检查：holder 可用、扩展已连接、测试账号已登录（登录状态由任务的 `precondition` 字段声明，或由你手动确认）。环境不满足则整体停止，不带着坏环境继续跑。

## 4. badcase 的收集

### 4.1 失败类别

每个未学会或评分失败的任务，归入以下类别之一，由运行器根据记录自动判定，判不了的标为 `unknown`：

| 类别 | 判定依据 |
|---|---|
| `env` | 环境检查失败、站点不可达、登录失效、出现验证码 |
| `record-empty` | 录制中没有任何与意图相关的动作 |
| `learn-failed` | 5 轮都没有通过 `demo` 试跑 |
| `test-failed` | 学会了（`demo` 通过），但 `test` 参数不通过 |
| `timeout` | 某个环节超时 |
| `unknown` | 其它 |

类别只是初步归类，不做根因判断。根因由人或我根据记录确认。

### 4.2 记录内容

每个 badcase 一个文件 `badcase.json`，固定包含：

- 任务 id、运行号、失败类别、失败环节。
- 录制目录路径。
- 每一轮学习的草稿 task 文件和它的运行输出（stdout、stderr、退出码）。
- 评分时的参数、输出和 `check` 结果。
- 人工备注字段（留空，由你补充根因，例如“选择器依赖动态 class”）。

### 4.3 根因的确认

badcase 的根因只在一个地方确认：人工备注。常见的根因方向：

- 录制缺了关键动作（看录制目录能否找到对应的操作）。
- 学习者误读了接口或页面结构（看草稿与录制的对应关系）。
- 草稿硬编码了演示值（用 `test` 参数跑必然失败，属于学习问题）。
- 站点改版（同一意图在页面上已经找不到入口）。
- `check` 写错了（人工判断结果其实正确）。

## 5. 如何反过来优化

### 5.1 闭环

1. 跑一次完整任务集，得到学会率、学习轮次、badcase 列表。
2. 对 badcase 按根因分组，找出最常见的一类。
3. 修改代码（录制、dev 驱动、task-lib）或任务本身（`check` 写错、站点改版后更新 `intent`）。
4. 重跑失败集合（不是全部），确认修复有效。
5. 把修复前后的结果对比，记录在一份改动日志里。

### 5.2 回归集

- 每个修复过的 badcase 保留为回归项，之后每次改动都要重跑。
- 回归项失败说明改动引入了新问题，优先处理。

### 5.3 防止只针对个别任务优化

- 每次修复的效果，要在至少两个不同的任务上体现，否则不算改进。
- 任务集本身的改动（增删任务、修改 `check`）单独记录，不与代码改动混在一起比较。

## 6. 任务来源与规模

- 第一版 30 个左右，覆盖常用站点（社交内容、搜索资讯、电商、办公协作、开发、招聘），每类 3 到 5 个。
- 任务由你提供意图，我来整理成格式。站点热门操作作为候选，需要你确认后才加入。

## 7. 结果的可信度

- 学习轮次依赖学习者模型。换模型后不能直接比较，要在同一模型下比较改动前后。
- 同一任务跑一次就可能偶然成功。学会率按任务数统计，不对单次结果做结论。
- 站点改版会让任务失效。失效的任务归入 `env` 或 `learn-failed`，并在报告里单列，不计入学会率的解释。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 学习者偷看到 `test` 参数 | 只把参数名交给学习者；评分脚本与学习者分开运行 |
| 学习者把演示值硬编码进草稿 | 评分时用 `test` 参数运行；硬编码的草稿在 `test` 上会失败 |
| 站点改版导致误判 | 归入 `env` 或 `learn-failed`，人工确认后再计入 |
| 中断后数据混乱 | 运行号固定，状态以 `status.jsonl` 为准 |

## 9. 与其它文档的关系

- 本文件只定义如何衡量学习效果，不改变录制与 dev 工具的设计。
- 与 [dev-tools.md](dev-tools.md) 的关系：dev 提供驱动和录制，任务集是使用它们做评测的方式。
