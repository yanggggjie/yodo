## 问题

### A. 测试方法与独立性

- **A1 录制前必须先探测页面**：没有先看真实链接和结构，直接猜选择器，场景连续失败。已改为先用探测脚本列出真实元素。
- **A2 覆盖的元素会被误点**：导航栏里有隐藏的同名链接，坐标点击落到了标题 `h1` 上。场景已加入 `elementFromPoint` 检查。录制本身正确记录了被点中的元素，问题在场景。
- **A3 IT 之家首页加载超时（偶发）**：驱动 `goto` 等待 `readyState === 'complete'`，广告多的页面超过 10 秒。重试后通过。见优化项 O2。
- **A4 学习的独立性**：苹果 task 学习前读过现有实现（它的 `parts` 常量与录制值相同），学习结果不能证明"只靠录制就能学会"。之后的站点只读头部注释。
- **A5 对照标准的局限**：现有 task 本身是标准答案。若现有 task 有错，新 task 与它一致也不代表正确。需要人工抽查真实页面结果。

### B. 学习（agent 这一步）

- **A6 选错锚点**：IT 之家搜索结果的第一个链接是图片链接（无文字），标题在同条目的文字链接里。学习时没有检查录制里的链接文字就写了选择器，结果标题为空。学习时应对每个选择器都在录制的页面快照上验证一遍。

### C. 录制与驱动

- **C1 Enter 不提交（已在驱动重写中解决）**：旧驱动只发 `keyDown` 没带 `text: "\r"`，搜索框回车无效。重写后驱动改为 `requestSubmit()`，但 IT 之家场景实际是点击"搜索"按钮完成的，驱动的 `press("Enter")` 路径还没有在真实站点上验证。
- **C2 录制名与 task 的 @record 对应**：每次录制都会加随机后缀，学习时要记下准确的录制名。已遇到多次手抄错误的风险。

### D. 现有 task 的问题（观察到，不修）

- **D1 苹果 task 写死机型列表**（`PARTS_BY_SLUG`）：页面上机型变化后结果不对，且不报错。这类 task 应该从页面或接口动态获取。
- **D2 苹果 task 的 `slug` 参数**：`ipad-pro` 只对应一个写死的 parts 列表，没有对应的录制。

- **B2 学习时域名没核对**：B 站动态接口在 `api.bilibili.com`，学习时写成了相对路径，发到了 `t.bilibili.com` 返回 404。学习时应以录制里请求的 `url` 为准，逐个核对域名和路径。
- **B3 学习时看错字段**：动态正文在 `desc.text`、`major.opus.title`、`major.archive.title` 三处，不同动态类型不同。学习时需要按录制里的样本逐类型确认，不能只看第一条。
- **B4 录制覆盖不足（材料问题）**：动态 1259021387446616089 的正文在 `feed/all` 里没有，现有 task 应该是通过另一个接口取的。演示时没有打开这条动态，所以录制里没有对应的请求，学习无从得知。演示应当覆盖"打开详情"这类操作。

- **C3 定位库：无障碍名称未规范化空白**：X 的"正在关注"标签无障碍名称是 `"Following "`（末尾带空格），`{ role: "tab", name: "Following" }` 精确匹配失败，超时。应对名称做空白规范化后再比较。（学习时以绕过为准，写在 task 注释里。）
- **C4 `expectRequest` 返回值类型不一致**：实现返回的 `body` 是响应文本字符串，但 `page.d.ts` 声明为 `{ body, base64Encoded }`。学习时按实现写，类型声明与文档（SKILL 写的是文本）都需要统一。
- **C5 第一次录制漏掉关键交互**：X 的第一次录制没有点"正在关注"，学到的是默认的"为你推荐"时间线（`HomeTimeline`）。学习者应检查录制里有没有目标接口，不对就要求重录，不能拿错接口凑合。

- **X1 当前结果不一致（未定位）**：学习出的 task 与现有 task 推文 ID 交集为 0（10 条），两边都不是严格按 `created_at` 倒序，说明两者取的数据或排序语义不同。待查：现有 task 用的是哪个接口和排序，新 task 是否应该按 cursor 或 entries 顺序返回。
- **X2 时间线实时变化**：两次连续运行的结果也不同，对照很难做到逐条一致，需要在同一时刻取快照比较，或只比较稳定字段。
- **X3 学习的 `x-client-transaction-id`**：直接复刻 HomeTimeline 请求返回 403，因为事务 ID 由页面脚本现算。这类接口只能让页面自己发请求后接住响应，不能复刻。
- **X4 录制时没有等待到位**：演示切换标签后时间线需要渲染，场景靠"≥3 条推文"等待判断，可能误判。

- **M1 现有 task 已失效**：`xiaomi-phone-models` 不论传什么关键词都返回 `[]`，且没有任何报错。页面结构或接口可能已经变了，现有 task 的"成功"只是空结果。
- **M2 录制覆盖不足**：演示只停留在 Xiaomi 分类（`cate_ids=3254`），没有切换 Redmi、POCO 等系列标签。学习出的 task 因此把分类 ID 写死，关键词 `redmi` 也找不到结果。演示应当覆盖"切换分类"，学习者应检查录到的分类参数是否只有一个。
- **M3 学习时的占位逻辑**：商品链接一开始写成了占位字符串，没有检查响应里是否已有 `gotoUrl`。学习时要逐个字段对照录制的响应，不能用猜的。

- **T1 淘宝风控阻塞**：录制中途出现 `punish`、`secaptcha`、`sec-captcha` 请求，商品列表接口没有加载，录到的只有空壳数据。自动化演示会触发风控，风控之后的数据不可用，测试结论无效。需要人工处理验证码后重录，或者接受这个站点在自动化下不可测。
- **T2 驱动：首页搜索提交无效**：驱动的 `click` 只派发 `click`，淘宝的搜索按钮不响应；完整的 pointerdown/mousedown/pointerup/mouseup/click 序列也无效；直接调用表单的 `requestSubmit()` 也不跳转。原因未定位（可能是站点的页面逻辑，也可能与风控有关）。直接打开结果页可以绕开，但这不是人的操作方式。
- **T3 录制的覆盖边界**：`mtop.*` 等接口的请求体带签名参数，不能复刻，只能让页面自己发请求后接住响应（同 X 的经验）。

- **I1 学习漏掉触发动作**：评论接口只在点击"评论"锚点后才请求，学习版直接打开文章，`expectRequest` 等不到请求。学习时应把"触发请求的那一步"（录制里紧挨着接口的动作）放进 `expectRequest` 的动作参数里。
- **I2 录制覆盖的翻页问题**：录到的评论是第一页（最新 28 层，倒序），学习版用的 1 楼恰好在第一页里。如果目标楼层不在第一页，学习版会报"第一页没有 1 楼"——这是正确的失败，但说明演示没有翻页，覆盖不足。

- **Z1 对照标准不对齐**：现有知乎 task 输出的是点赞状态（`liked`、`label`、`already`），没有回答 ID 或标题，学习版的输出无法与之逐字段比较。测试标准要求"结果一致"，就得约定两边输出同一个标识（例如回答 ID），或者现有 task 的输出需要扩展。点赞的那一步也没有覆盖（允许副作用，但本轮只做了只读部分）。
- **Z2 搜索高亮标签**：标题里带 `<em>` 高亮，学习时漏掉了清理，已修正。

- **X5 检索材料的脆弱性**：录制目录里同时有页面 HTML 和接口 JSON，文件名只差 `.response.json`，用 `grep` 按接口名查容易取到 HTML。学习工具应按时间线里的 `file` 字段取文件，不要按文件名猜。

## 优化点（只记录）

- **O1 驱动的等待**：`goto` 只等 `readyState` 和地址变化，广告和第三方脚本会拖慢它。可以改为等待主文档的 `load` 事件加一个较短的超时，超时后继续。
- **O2 录制与学习的材料**：学习时 agent 需要 `selector` 在页面快照上是否唯一的信息，录制时记录"该选择器匹配到的元素数量"会更可靠。
- **O3 `record-run` 的重复代码**：场景里的 `waitFor`、滚动、点击辅助函数在每个站点都要写一遍，应当沉淀成 dev 驱动的一部分（但不进产品代码）。
- **O4 探测与录制分开**：探测用的录制会留下临时记录，需要手动 abort。探测应该不走录制。
- **O5 学习结果的验证**：学习出的 task 应该自动附带"选择器在录制快照里的命中数"检查，减少人工比对。
